# Independent Implementation Audit — 2026-10-16

Scope: branch `arena/4e19a156-vantera-membership-platform`, full read of
migrations, RLS, storage config, server actions, route handlers, auth, payment
workflow, PII handling, docs, tests, and packaging. Method: static verification

**Update (end of change-set):** ALL findings below were corrected in code; the
fixes are described inline ("→ Fix") and the exact verification results are in

(`create_order` RPC, idempotency key) were made TRUE by implementing the
features, not by softening the docs.

## Findings (ranked by severity)

### HIGH

**H1. Server-side price snapshot is not enforced at the database boundary.**
`createOrderAction` snaps the price correctly in app code, but the
`orders_self_insert` RLS policy checks only `user_id = auth.uid()`. Anyone
holding the **public anon key** can POST a `REST /orders` row with
`unit_price = 0.01`, a fabricated `tier_name_snapshot`, and own a ready-to-pay
order. Documentation (`docs/architecture.md`, `docs/payments.md`, README)
claimed a server-definer `create_order()` RPC enforces this — **no such RPC
exists anywhere in the repo** (`grep rpc(` returns only `verify_card`).

→ Fix: real `security definer create_order(p_tier_id)` RPC that performs the
tier lookup, snapshot, active-profile guard, open-order cap, and insert
atomically under a per-user advisory lock; drop the direct INSERT policy;
order action calls the RPC.

**H2. Duplicate open payment submissions possible (check-then-insert race).**
`ensureOrderAcceptsPayment` reads, then inserts. Two concurrent submissions
(parallel tabs/API calls) for one order both pass the gate and create two
independent `pending_review` payments — double the review surface, double
evidence, possible double issuance if both were approved in wrong order.
Docs claimed a `client_request_id` idempotency key — **does not exist**.

→ Fix: partial unique index `one_open_payment_per_order` over open statuses
(stronger than any app-level check), friendly error mapping, plus resubmission
by in-place replace (see M1).

### MEDIUM

**M1. No member resubmission path after "additional information required".**
The reviewer can request more information, but the member can only upload
evidence — they cannot correct the payment itself (amount, asset, tx hash,
issuer), and nothing returns the payment to `pending_review`. The reviewer
must manually mark it under review again — a workflow dead-end.

→ Fix: `resubmitCryptoPaymentAction` / `resubmitGiftCardPaymentAction` doing
an ownership- and status-guarded **in-place replace** of the same payment row
(status → pending_review, version++), review history entry, order mirror —
with a conditional update that fails politely if a reviewer has already
picked the payment up (`under_review`). UI replaces the plain submission form
with a pre-filled edit form while the payment is in a re-openable state.

**M2. Review actions do not consider the order's own lifecycle.**
`paymentReviewAction` never loads the order's status: a reviewer can approve
a payment belonging to a **cancelled order**, minting a membership from a
dead order.

→ Fix: approve/reject/info decisions are refused when the order is
`cancelled` (conditional `WHERE` on the payment update kept as the
concurrency anchor).

**M3. Open-order cap is a TOCTOU check in the request path.**
Two concurrent `createOrderAction` calls both observe `count < 3` → 4+ open
orders. Also, admins (who see other users' orders) hit the cap early because
the count is not user-scoped under their wider RLS visibility.

→ Fixed as part of H1 (check happens inside the locked RPC, per-user).

### LOW

**L1. Evidence rollback delete runs with the member client.**
`supabase.storage.remove()` in `uploadEvidenceAction` can never succeed —
there is deliberately no DELETE policy on `storage.objects` for members.
The orphaned object remains (metadata insert failed).

→ Fix: rollback via service-role client.

**L2. Documentation overclaims.**
README / architecture / payments docs describe mechanisms that did not exist
before this audit (`create_order` RPC, `client_request_id`, DB-driven order
creation). These are corrected in the same change-set that *makes* the claims
true.

**L3. Per-IP rate limiting trusts `x-forwarded-for`.**
Fine on Vercel; spoofable on naive self-hosts. Documented in
`docs/security.md` + deployment notes; no code change.

### INFO / verified-OK during inspection

- RLS write policies: customers cannot UPDATE orders/payments/memberships/
  roles; inserts restricted to own rows with `status IN (pending_review,
  submitted)`; history/audit tables have **no** INSERT privileges for clients.
- Separation of duties: approve/reject require distinct permissions; **any**
  reviewer holding approve rights is additionally blocked from reviewing a
  submission they own (`payment.user_id = ctx.user.id`) — the
  "customers can approve their own payments" path is closed.
- Review decision concurrency: conditional `UPDATE ... WHERE id AND version
  AND status IN (...)` — second reviewer gets "already processed"; history
  row only written on success.
- Membership activation gated on approved payment + ready card (app-level),
  with epoch reset fields per transition; orders mirror guarded by
  conditional status.
- Card download route: ownership re-check + member `ready` gate + admin
  `?version=` limited to `cards.manage`; 404 over 403 (no IDOR oracle).
- Evidence route: RLS-scoped row lookup, 120 s signed URLs, private bucket,
  rate-limited.
- Upload pipeline: extension allowlist → declared-MIME check → **magic-byte
  sniffing** → size caps (10/15 MB, under 25 MB bucket hard cap) → random
  server-generated object names (original names — potential PII — discarded
  for paths; kept only in metadata `file_name` for display).
- Verify page: SQL function returns only the whitelisted tuple; 32-hex
  pattern enforced inside SQL; generic "not recognised" for unknown IDs (no
  enumeration oracle); unit tests guard the payload serializer keys.
- Gift cards: strict schemas reject any unknown field (pin/cardNumber/
  redemptionCode tested), digit-run screening of notes/reference, review UI
  carries issuer-terms warning, method disabled by default.
- Email: no provider = deliberately no delivery (never faked); templates
  contain references, amounts and reasons only.
- Auth: SSR cookie sessions, `getUser()` re-validation, uniform login error,
  password reset through `/auth/callback?type=recovery`, per-IP rate limit.
- Bootstrap: `scripts/grant-admin.mjs` service-operated only; no in-app path
  grants the first administrator.
